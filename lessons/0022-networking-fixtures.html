URLSession：HTTP 校验与可测试的数据边界

把网络传输、HTTP 语义与 JSON 结构区分开，才能为原生页面提供可靠状态。

前置：21 MainActor：UI 状态、重入与默认隔离

本课的一个成果通过可注入 transport 加载、校验并解码一个网络模型。

给 I/O 一个窄接口

HTTPTransport 只负责根据 URLRequest 返回 Data 与 URLResponse。LiveTransport 调用 URLSession.data(for:)；FixtureTransport 返回内存中的固定响应。ProfileClient 不关心数据是否来自公网，所以同一条状态码校验和 Codable 解码路径可离线运行。协议不是为了给每个类型套一层抽象，而是隔开变化大、速度慢、难确定的 I/O 边界。

public protocol HTTPTransport: Sendable {
    func data(for request: URLRequest) async throws -> (Data, URLResponse)
}
// 真正联网的实现；默认 CLI 刻意使用 fixture。
return try await session.data(for: request)

成功接收字节还不等于业务成功

URLSession 可以成功返回一个 HTTP 503 响应，因此必须先确认 HTTPURLResponse，再检查接受的状态码，之后才能解码。这里的教学接口接受 200..<300，并要求响应体包含完整 ReaderProfile；204 若没有正文，仍会得到 DecodingError。这是接口契约，需要与你的服务端约定一致。保持 HTTPError 与 DecodingError 区别，UI 才能决定重试或报告数据格式问题。

guard let response = response as? HTTPURLResponse else {
    throw HTTPError.nonHTTPResponse
}
guard (200..<300).contains(response.statusCode) else {
    throw HTTPError.unacceptableStatus(response.statusCode)
}
return try JSONDecoder().decode(ReaderProfile.self, from: data)

用 fixture 检验真实边界

示例 URL 使用 example.invalid，但 fixture 不会请求它，避免把外网可用性混入课程验证。测试分别覆盖合法 JSON、HTTP 503、非 HTTP 响应、id 类型不符。传输层错误直接传播，取消在 I/O 前后检查，UI 再区分取消与普通故障。接真实服务时还要确认认证、缓存、超时与隐私约束；不要把令牌写在示例中，也不要为了联网成功关闭平台传输安全。

动手：构造状态码 503 且正文非法 JSON 的 fixture，判断首先得到哪种错误。

  1. 运行 network 演示。
  2. 阅读 fixtureDecodesAndRejectsHTTPFailure 测试。
  3. 把 JSON 中 id 从数字改成字符串，保持 HTTP 200，运行测试观察 DecodingError。
验收现象

503 优先得到 HTTPError；200 且字段类型错误得到 DecodingError。

先独立完成，再展开参考解法

检验顺序不能反过来。先解码错误正文，可能把真正的服务端不可用误报成 JSON 问题。当前 fetch 先做状态校验，所以 503 加上 not JSON 仍稳定产生 unacceptableStatus(503)。

let client = ProfileClient(transport: FixtureTransport(json: "not JSON", status: 503))
do { _ = try await client.fetch(from: url) }
catch { print(error) } // unacceptableStatus(503)

从前端迁移时，留意这些误区

  • 把 HTTP 404 当成 URLSession 必然抛出的传输错误。
  • 仅对成功 JSON 写测试。
