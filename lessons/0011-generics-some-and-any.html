分清泛型、some 与 any 的类型选择权

不要把 some 与 any 记成性能好坏的口号。先问谁选择具体类型、是否需要保留类型关系、是否真的要混装不同类型。

前置：10 用协议表达能力，用扩展共享实现

本课的一个成果实现保序去重，并为同构算法、隐藏返回类型和异构存储选择合适的类型形式。

泛型把类型关系写进算法

unique<Element: Hashable> 表示调用者选择 Element，但输入与输出使用同一个 Element。约束让函数能借助 Set 判定重复，而不需要转换为 Any 再强转回来。数组的顺序来自原输入，Set 只负责成员检测，因此既能去重又保留首次出现的位置。只写 Set(elements) 虽然去重，却会丢掉顺序承诺。

public func unique<Element: Hashable>(_ elements: [Element]) -> [Element] {
    var seen: Set<Element> = []
    return elements.filter { seen.insert($0).inserted }
}
print(unique([3, 1, 3, 2]))          // [3, 1, 2]
print(unique(["Swift", "UI", "Swift"])) // ["Swift", "UI"]

some 隐藏具体名字，但保持一个确定的底层类型

函数返回 some StudyDescribing 时，具体类型由函数实现决定，调用者只依赖公开的协议能力。同一个返回声明需要维持一致的底层类型，不能随某个 if 随意返回 Reading 或 StudySession。SwiftUI 的 some View 也利用这种类型身份；视图构建器能将条件包装成一个确定的复合类型，不代表 some 变成了任意混装容器。

public func starterReading() -> some StudyDescribing {
    Reading(title: "The Swift Programming Language", minutes: 20)
}
let reading = starterReading()
print(reading.summary())

参数位置的 some Protocol 是泛型参数的便捷写法，具体输入仍由调用者选择；不要把“返回值由实现者选择”机械套用到所有 some 出现的位置。

any 为运行时容纳不同实现付出抽象成本

any StudyDescribing 是存在类型，能容纳不同的符合类型。数组 [any StudyDescribing] 可以同时放 Reading 和 StudySession；取出元素后只能依赖协议暴露的能力。它会隐藏一些具体类型关系，并可能带来装箱与动态派发成本，但不要未测量就断言所有 any 都会堆分配或造成性能问题。

let items: [any StudyDescribing] = [
    starterReading(),
    StudySession(title: "泛型", minutes: 30)
]
print(summaries(items))

选择顺序：类型已经清楚就使用具体类型；多个类型共享同一算法且需保留关系时用泛型；返回值想隐藏实现但保持身份时用 some；明确需要异构存储或运行时替换时用 any。

先独立完成，再展开参考解法
public func unique<Element: Hashable>(_ elements: [Element]) -> [Element] {
    var seen: Set<Element> = []
    var result: [Element] = []
    for element in elements {
        if seen.insert(element).inserted { result.append(element) }
    }
    return result
}

这份循环版本与仓库实现相同，但更容易逐步调试。类型信息贯穿输入、Set 和返回数组，没有一次 Any 强制转换。

从前端迁移时，留意这些误区

  • any 不是“没有类型检查”，仍受协议能力约束。
  • 不要只为了消除编译错误，把所有泛型返回值都改成 Any。
