AsyncSequence 与回调桥接：结束也属于契约

一次结果与连续事件使用不同抽象，都必须设计完整的结束路径。

前置：22 URLSession：HTTP 校验与可测试的数据边界

本课的一个成果消费一个可停止的事件流，并将单次回调桥接为 async。

连续状态用 AsyncSequence

AsyncStream 把多次 yield 转成 for await。ProgressFeed 的生产者每次发出进度，消费者逐项处理，等不到值时可以挂起。bufferingNewest(1) 只保留最新待消费进度，适合“当前位置”这类状态；若每条事件都是必须保存的交易，丢旧值就不合适。设置缓冲上限不是自动背压，生产者仍可继续发送，需观察 yield 结果或选用能限制生产速度的协议。

let feed = ProgressFeed(count: 3)
for await progress in feed.stream {
    print(progress)
}
await feed.waitUntilStopped()

终止需要回传给生产者

生产者用 defer finish 告诉消费者以后没有值，onTermination 再取消生产 Task 并清理外部资源。提前 break 并不等于一个可靠、即时的取消通知，特别是你还持有 stream 或 continuation 时；本例明确提供 feed.cancel。测试检查消费者取消后生产者退出、终止回调发生，以及提前 break 后显式关闭。真实传感器或通知监听还要在同一路径注销 observer，避免页面离开后继续耗电。

for await progress in feed.stream {
    print(progress)
    break
}
feed.cancel() // 提前退出时由所有者关闭。
await feed.waitUntilStopped()

单次回调必须恰好恢复一次

withCheckedThrowingContinuation 适合“最终只回调一次”的旧接口。成功和失败通过 Result 合并成一个 resume(with:) 路径，避免漏掉某条分支。checked 会帮助发现重复恢复或遗漏，但不替你自动修复，更不会自动取消底层工作。本例旧 API 同步且保证恰好一次回调；若真实 API 可能永不回调、重复回调或需要取消 token，就必须另外设计同步保护与取消握手，不能照搬成生产适配器。

let title: String = try await withCheckedThrowingContinuation { continuation in
    legacyTitle(succeeds: true) { result in
        continuation.resume(with: result) // 一个结果、一次恢复。
    }
}

验收现象

消费者退出后生产者完成；单次桥接成功返回标题，失败保持 LegacyFailure。

先独立完成，再展开参考解法

流的 finish 可结束迭代，Task 的取消负责通知生产者。二者职责不同，完整适配通常需要两者连接。单次 continuation 的 resume 不能像 AsyncStream.yield 一样多次调用；如果旧接口实际上会重复提供进度，应改为流。

从前端迁移时，留意这些误区

  • 把 AsyncStream 的缓冲上限误认为生产者背压。
  • 对会多次回调的接口使用单次 continuation。

即时自测

withCheckedContinuation 会自动让一个永不回调的旧 API 支持取消。
