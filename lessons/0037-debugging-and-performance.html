前置：36 用测试描述用户能依赖的行为

本课的一个成果采集一段性能证据，指出瓶颈所在，而不是凭 UI 观感猜测。

先区分三类问题

编译错误看诊断和调用上下文；运行崩溃看堆栈与出错线程；卡顿看时间采样。开始时记录设备、OS、Debug/Release、数据规模与复现操作。Debug 下的卡顿可帮助定位，但不能当作发布版性能数字。

为一次保存操作设置断点，运行到断点后用 Variables 查看草稿与实体。Step Over 看当前层的流程，Step Into 进入调用，Continue 恢复。条件断点能只在空标题或特定 ID 时停下，比到处打印内容更精确。

CPU 与内存分别寻找证据

在 Product → Profile 中选择 Time Profiler，重复触发你观察到的慢操作，选中时间范围再看热点调用。若 MainActor 上解析大量 JSON 或排序，先减小输入验证瓶颈，再考虑迁移计算边界。换成 async 函数不会自动让 CPU 工作离开主 actor。

Memory Graph 适合查对象之间的持有关系，Allocations 适合看数量和存活趋势。反复打开并关闭详情页后若对象持续增加，检查闭包、计时器、观察者和任务的持有链；weak 只有在不应持有时才使用，不是普适修复。

日志只记录对定位有帮助的信息

用 Logger 按 subsystem/category 分组。避免记录用户笔记、令牌和完整请求体；在日志中保留事件类型、非敏感数量与错误类别通常就能定位。保存开始与结束两个日志可解释顺序，但精确耗时分析应使用 Instruments 或 signpost。

import OSLog
let logger = Logger(subsystem: "learning.native", category: "storage")
let itemCount = 3
logger.info("Save completed; count=\(itemCount)")

验收优化时固定同一输入和环境，记录改前改后的耗时、内存与交互表现。若只改了实现却没有可比较测量，只能说“已重构”，不能说“已优化”。

动手：做一次可复现的性能观察

  1. 以 Release 配置 Profile NativeStudy，保存一条固定标题的记录。
  2. 记录 Time Profiler 中主要工作及其线程。
  3. 连续开关详情 20 次，在 Memory Graph 检查未释放的编辑器或 loader。
  4. 写下一个有证据的结论和一个未验证的假设。
验收现象

得到附环境与操作的观察记录；不把一次采样中未出现问题当作永久无泄漏。

先独立完成，再展开参考解法

如果没有观察到异常，记录“当前数据规模、20 次路径未发现持续增长”，而非强行制造优化。若看到主线程 I/O，先把测试数据和测量窗口固定，再尝试拆出服务，重复相同操作比较。任何实验性阻塞代码在提交前删除。

从前端迁移时，留意这些误区

  • SwiftUI body 执行次数不等于实际屏幕绘制次数。
  • 看到 retain cycle 先画强引用路径，避免无差别添加 weak。

即时自测

把耗时排序函数加上 async，就能保证它在后台线程执行。
