把 UIKit / AppKit 控件接入 SwiftUI

原生工程师既要会 SwiftUI，也要能读懂和接入现有 UIKit、AppKit 代码。

前置：38 让 Mac 应用像一个 Mac 应用

本课的一个成果沿着双向数据流解释一次原生文本控件编辑，并避免重复写入。

两个方向，两个入口

SwiftUI 嵌入 UIKit View 使用 UIViewRepresentable；嵌入 AppKit View 使用 NSViewRepresentable。make 方法创建原生控件，update 方法把新的 SwiftUI 输入应用到已有实例。不要每次更新都重新创建控件，否则选区和输入状态容易丢失。

另一方向是 UIHostingController / NSHostingView：把 SwiftUI 放入现有平台界面。选择方向取决于页面的所有者；并非项目使用 SwiftUI 后就再也不能使用平台框架。

Coordinator 是事件回流的适配器

原生控件的 delegate 或 target-action 把用户事件交给 Coordinator，再修改 Binding。Binding 的所有者仍在 SwiftUI。Representable 是值，会被重新创建；Coordinator 是可持续存在的对象，update 中应让它引用最新的 Binding。

// iOS 完整实现见 NativeBridgeWorkshopView.swift。
func updateUIView(_ field: UITextField, context: Context) {
    context.coordinator.text = $text
    guard field.markedTextRange == nil, field.text != text else { return }
    field.text = text
}

这两个判断分别保护输入法组合态、避免相同值重复赋值。中文输入尚未完成时覆盖 text，可能打断候选过程；不能只用英文键盘测试就宣称可用。

布局与清理也有归属

SwiftUI 管理被包装视图的布局，不应从原生控件内部随意修改其 frame 来对抗外层布局。需要提供尺寸时研究 representable 的 sizeThatFits；监听外部资源时在 dismantle 阶段清理。

样例是教学用单行文本桥接，不是完整富文本编辑器。生产编辑器还要处理选区恢复、撤销、焦点、组合输入、辅助功能与平台差异。先完成最小双向数据流，再逐项增加功能。

  2. 先在 SwiftUI text 输入，再在 Native text 输入；观察底部文本。

  4. 在 update 和 Coordinator 回调分别打断点，记录调用方向。
验收现象

两种控件共享最终提交的文本；组合输入过程中不会被另一方向的重复更新打断。

先独立完成，再展开参考解法

保留 @State 为唯一真值。事件方向是原生用户输入 → Coordinator → Binding → State；渲染方向是 State → update → 原生控件。相同值不写入，组合态不覆盖。若焦点行为仍异常，先记录 OS 与输入法，不要用不断 dispatch 到下一帧掩盖循环。

从前端迁移时，留意这些误区

  • 原生控件状态不等于 DOM 属性，反复写入可能重置输入中的状态。
  • 桥接不是只把类型包起来，还包括生命周期、布局与事件语义。

即时自测

makeUIView 创建控件，updateUIView 把新的输入同步到已有实例。

合上页面，尝试回忆

  • Coordinator 为什么要更新其 Binding？
  • 组合输入和最终提交的字符串有什么不同？
