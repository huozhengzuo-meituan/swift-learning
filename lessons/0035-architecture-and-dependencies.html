让业务规则离开 View

不必先选择架构缩写。先回答：谁拥有状态，谁实施规则，谁触发不可逆的操作？

前置：34 动画、无障碍与本地化

本课的一个成果画出一条“输入 → 校验 → 保存 → 呈现错误”的依赖路径，并替换一个依赖。

从一个失败场景开始划分职责

设想用户输入三个空格后点击保存。如果只有按钮的 disabled 判断，别的调用入口仍能写入空标题。把“标题必须有可见字符”放入独立规则后，视图负责提示，保存入口仍负责拒绝。界面是交互适配层，不能成为唯一的数据防线。

NativeStudy 的 StudyEditorView 保存草稿；StudyItem 与保存逻辑表达数据约束；ResourceLoader 承担异步资源状态。先读代码中的调用方向，再决定是否抽 protocol。项目规模小时，一个清晰函数通常比五层空壳更好。

依赖注入是把选择放到边界

第 22 课的 HTTP transport 可用固定响应替换。核心逻辑只依赖“能取得响应”这个能力，测试不依赖外网。你可以从普通初始化参数开始注入，不必引入 DI 容器。对 SwiftData 小项目，直接在边界使用 ModelContext 也是合理选择；无需为每个类型创建 Repository。

struct TitlePolicy {
    static func normalize(_ input: String) -> String {
        input.trimmingCharacters(in: .whitespacesAndNewlines)
    }
}
// Foundation 中的 String 工具。调用方先标准化，再做空值/长度校验。

依赖有不同生命周期：一次操作、一个页面、一个窗口、整个应用。把所有东西放在环境里会隐藏这些差异。环境传入的依赖需要在 Preview 中同样提供，否则预览可能缺少运行条件。

数据流能解释，架构才有价值

画一条真实路径：编辑标题 → 草稿变化 → 保存按钮 → 校验 → ModelContext 保存 → 成功关闭 / 失败展示。标出 MainActor 和持久化边界。共享偏好在 App 中创建，窗口状态留在窗口；这能解释为什么开两个窗口时有些值共享，有些不共享。

一个可维护的设计应能回答“离开页面是否取消请求”“存储失败是否保留草稿”“列表和详情是否指向同一实体”。为这些问题加测试，比争论 MVVM 与 MVC 名称更能检验你的理解。

动手：给空白标题规则找到唯一的执行入口

  1. 运行 NativeStudy，输入空白标题并观察。
  2. 读 StudyItem、StudyEditorView 和测试文件，画出保存调用路径。
  3. 增加一条带首尾空格但中间有效的标题用例；确认标准化之后保存。
验收现象

空白输入不会插入记录；有效标题去掉外围空白后保存；即使绕过按钮调用保存逻辑，约束仍成立。

先独立完成，再展开参考解法

让保存操作先取得标准化结果，统一校验，再修改模型并保存。UI 可以提前禁用按钮帮助用户，但仍在操作边界校验。测试直接调用规则/操作，而非只检查 disabled 的布尔表达式。失败时不要先清空草稿。

从前端迁移时，留意这些误区

  • 不要把 React 的全局 store 习惯直接套到所有原生页面。
  • @Observable 提供观察能力，不会自动提供网络、事务或并发隔离。

即时自测

抽象应围绕业务边界与替换需求设计，而非给每个 View 固定加层。

合上页面，尝试回忆

  • 为什么 UI 校验不能代替保存入口校验？
  • 如果离开页面后请求还在进行，哪个对象应该负责取消？
