用测试描述用户能依赖的行为

测试最有价值的部分，是证明错误输入、取消和重启等情境下用户仍能依赖应用。

前置：35 让业务规则离开 View

本课的一个成果为同一功能选择合适的单元、集成和界面验收，并写出失败路径。

测试层次由证据决定

标题校验适合纯函数测试；SwiftData 保存后能否重新读取适合集成测试；用户是否能打开编辑页并保存适合 UI 测试。同一断言不必在每层重复。Swift Testing 用于现代单元/集成测试；XCTest 与 XCUIAutomation 承担 UI 自动化。它们可以存在同一工程，不要在同一个测试函数中混用断言体系。

读 NativeStudy 的测试：新 ModelContext 读取能证明持久化到该测试存储，而同一对象上刚改的属性只能证明内存赋值。测试中使用内存容器是为了隔离用户数据，不等价于证明磁盘迁移。

测试输入应该击中边界

不要只测“Swift”这个正常标题。加入空字符串、空格、emoji、临界长度和超长字符；文字长度是 Character 语义，不能照搬 UTF-16 下标。异步测试使用固定输入和控制时序的方法，避免用随意 sleep 等待一个“应该已完成”的事件。

import Testing

@Test("标题可以包含中文与组合字符")
func titleCharacters() {
    let title = "学习👩🏽‍💻"
    #expect(title.count == 3)
}
// 这个例子只验证字符串语义；业务测试应调用真实校验函数。

把界面验收写成可复现旅程

设计一条旅程：启动独立测试存储 → 新建条目 → 输入标题 → 保存 → 列表显示 → 重开应用 → 条目仍在。为按钮提供稳定的 accessibilityIdentifier，UI 测试不要依赖界面坐标或翻译后的文案。

只在 UI 测试 target 中引用 XCUIApplication。等待可见条件用 waitForExistence(timeout:)，随后断言结果；设置了 timeout 仍不代表可以忽略返回值。执行 UI 自动化需要模拟器或真实运行环境，swift test 不会自动点界面。当前仓库是否实际完成 UI 自动化，以 VERIFICATION.md 为准。

动手：为“删除条目”写一张三层证据表

  1. 在 Xcode 按 ⌘U 运行 macOS 单元测试。
  2. 找到删除测试，确认它读取的是保存后的新上下文。
  3. 在 iOS 模拟器手动新建、编辑、删除，再重启；记录 OS、步骤、预期与结果。
  4. 扩展练习：新增 UI Testing Bundle，把这条路径写成 UI 测试。
验收现象

能明确说出哪些行为已有自动化证据、哪些是手工验证、哪些尚未覆盖。

先独立完成，再展开参考解法

规则层：不存在的条目如何处理；集成层：删除后 fetch 为空；UI 层：触发删除后列表与详情都保持一致。记录测试运行命令与结果。不要用单元测试通过推导“VoiceOver 已通过”或“真机已通过”。

从前端迁移时，留意这些误区

  • 断言执行了并不表示断言有效：先确认它能够在错误实现下失败。
  • 不要让共享单例或真实网络决定测试结果。
