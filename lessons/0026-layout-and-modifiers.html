布局与修饰器：理解包裹顺序

从 CSS 转向 SwiftUI 时，先理解父级提议尺寸、子级选择尺寸、父级放置子级的协作。

前置：25 从 App 到 View：声明式界面的边界

本课的一个成果通过交换 padding 与 background，预测并验证布局结果。

栈表达关系，尺寸随内容变化

HStack 横向排列，VStack 纵向排列，ZStack 叠放。示例行用 firstTextBaseline 对齐图标和文字，用内层 VStack 表示标题和时间的组合。SwiftUI 布局不是给每个元素套 CSS 样式再执行网页排版；容器向子视图提供尺寸约束，子视图据此报告尺寸。使用 .font(.headline) 等语义字体让界面适应阅读偏好，别提前固定每行文字高度。

HStack(alignment: .firstTextBaseline, spacing: 12) {
    Image(systemName: "book")
    VStack(alignment: .leading, spacing: 4) {
        Text("SwiftUI 数据流").font(.headline)
        Text("State → Binding").font(.caption)
    }
}

修饰器返回新视图，顺序会改变含义

每次修饰器调用都可以理解为给前面的视图加一层包装。先 padding 再 background，背景覆盖留白；先 background 再 padding，留白落在背景之外。frame 并不是直接改掉所有内部视图尺寸，而是参与外层布局约束；offset 主要改变显示位置，不能用来替代兄弟视图正常排布。这些区别解释了为什么照搬“先写 margin 再写颜色”的 CSS 心智会产生误判。

// 蓝色背景包含 24 点留白。
Text("Padding then background")
    .padding(24)
    .background(.blue.opacity(0.2))

// 留白位于蓝色区域之外。
Text("Background then padding")
    .background(.blue.opacity(0.2))
    .padding(24)

让布局承受真实内容

LayoutWorkshopView 使用 ScrollView 处理超长内容，VStack 沿 leading 对齐，再用 frame(maxWidth: .infinity, alignment: .leading) 把剩余空间分配到外层。测试时要拉窄窗口、输入长中文和较长英文、增大辅助功能字号。文字在正常尺寸好看不代表布局合格；宁可允许多行并滚动，也不要通过缩小字体掩盖信息。GeometryReader 和自定义 Layout 留到测量确有必要时再引入。

VStack(alignment: .leading, spacing: 24) {
    Text("一段会随着宽度自动换行的学习说明")
        .font(.body)
}
.frame(maxWidth: .infinity, alignment: .leading)
.padding()

验收现象

两种背景范围确实不同；长标题完整显示，布局不会依赖固定文本高度。

先独立完成，再展开参考解法

将 padding 放到 background 前，让卡片底色包含内部留白；外部卡片间距交给父 VStack 的 spacing。

VStack(alignment: .leading, spacing: 8) {
    Text("理解 SwiftUI 的布局协作").font(.headline)
    Text("先预测，再运行验证。")
}
.padding()
.background(.blue.opacity(0.1), in: RoundedRectangle(cornerRadius: 12))

从前端迁移时，留意这些误区

  • 不要把 padding 当成与顺序无关的 CSS 属性。
  • 不要用大量 offset 修补本应由容器表达的布局关系。

即时自测

padding 与 background 调换顺序，可能改变背景覆盖的区域。
