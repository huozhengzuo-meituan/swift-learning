async let：固定数量的结构化子任务

名字与未读数相互独立，可以同时开始，但其生命周期仍属于当前函数。

前置：15 async / await：挂起、恢复与错误

本课的一个成果用 async let 并发加载两份独立数据并组合成一个值。

先找依赖，再创建子任务

本例界面需要名字与未读数。顺序版本没有数据依赖，却要等名字完成才开始第二步。将两个声明改成 async let，会创建两个结构化子任务；在真正组合 Dashboard 时才等待结果。可以把它与 Promise.all 的“多个独立请求汇合”类比，但 Swift 还把子任务的生存范围限制在词法作用域里。不要为了看起来高级，把本来需要前一步 ID 的请求强行并发。

async let name = loadName()
async let count = loadUnreadCount()
// 从此处开始需要两项值，等待并合成。
return try await Dashboard(name: name, unreadCount: count)

作用域是生命周期边界

async let 不会把任务偷偷留在函数之外。离开作用域时，尚未等待的子任务会被取消并等待结束；取消是合作式的，所以一个不响应取消的任务仍会拖延退出。这个约束让调用者知道 loadDashboard 返回时，其子工作已经收尾。与随手创建 Task 再丢弃句柄相比，你不必为这两项短期工作设计额外持有者。

func previewOnly() async throws -> String {
    async let name = loadName()
    async let count = loadUnreadCount()
    _ = try await count // 读取也可能传播子任务错误。
    return try await name
}

结果顺序不等于完成顺序

name 和 count 哪个先完成并不影响 Dashboard 的字段含义。读取某个 async let 时会等待它并传播它的错误；“某个子任务已经失败”不代表父任务此刻自动跳进 catch。需要观察结果，错误逃出作用域后其余未完成工作才按结构收尾。测试关注返回字段和错误契约，不应断言短睡眠的精确耗时。这里的固定两项工作适合 async let；数量来自用户列表时下一课用任务组。

先独立完成，再展开参考解法

头像请求如果不依赖 name/count，应与二者相邻声明；若依赖服务端返回的用户 ID，则应先等待 ID，再开始头像工作。现有可运行解答就是 loadDashboard；不要为追求并行引入不存在的数据依赖。

async let name = loadName()
async let count = loadUnreadCount()
let dashboard = try await Dashboard(name: name, unreadCount: count)
print(dashboard)

从前端迁移时，留意这些误区

  • 认为两个 async let 的完成顺序等于声明顺序。
  • 认为取消子任务会立即强制终止它。

即时自测

async let 的子任务会在所在作用域结束前被收束。
