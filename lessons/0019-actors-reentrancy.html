Actor：隔离状态与 await 后的不变量

编译器能防止数据竞争，但“只剩一张票”仍需要正确的业务时序。

前置：18 Task 生命周期与合作式取消

本课的一个成果用 actor 实现并发预约，并证明挂起时不会超售。

状态与操作放进同一个边界

SeatInventory 保存 available，调用者通过 actor 方法预约或查询。外部调用需要 await，因为可能要进入 actor 的执行器；这不表示 actor 为自己独占一条线程。与前端模块里的普通共享变量相比，actor 把允许访问这份可变状态的边界写进类型。把所有状态机械地塞进一个巨型 actor 也不可取，应按一致性需求建立边界。

let seats = SeatInventory(capacity: 1)
async let first = seats.reserve { /* 异步确认 */ }
async let second = seats.reserve { /* 异步确认 */ }
let results = try await [first, second]
print(results.filter { $0 }.count) // 只能有一个成功。

重入会打断检查后的假设

错误实现是先 guard available > 0，再 await confirm，最后 available -= 1。第一个调用挂起时，第二个调用也可能看到库存为一，于是两次都成功。没有两个线程同时写同一变量，仍然会超售：这是逻辑竞争。正确实现把检查和占位放在同一个不含 await 的片段里；在挂起前，库存已经是零，其他调用看到的状态仍满足不变量。

guard available > 0 else { return false }
available -= 1 // 先占位，再允许重入。
do {
    try await confirm()
    try Task.checkCancellation()
    return true
} catch {
    available += 1 // 失败或取消时归还占位。
    throw error
}

证明范围要说清楚

测试把第一位预约固定在 confirm 的挂起点，此时检查剩余量为零，并断言第二位失败，然后才放行第一位。另一组测试验证确认失败或取消后库存恢复为一。这里证明的是本进程内的预约不变量。若 confirm 真的扣款，不能简单靠加回库存完成跨系统事务；需要服务端幂等键、订单状态与补偿策略。actor 也不保证调用按你发起的顺序公平排队。

验收现象

无论哪位先获得执行机会，成功数均为一，库存为零。

先独立完成，再展开参考解法

可行时间线：A 读到 1，立即写成 0，然后挂起；B 读到 0，直接返回 false；A 恢复并返回 true。关键不是 A 一定先执行，而是每个预约在挂起前占位。删除占位并把减库存移动到 await 后，会让门闩测试直接揭示缺陷。

从前端迁移时，留意这些误区

  • 把 actor 当成覆盖整个 async 方法的互斥锁。
  • 把内存状态回滚误认为完成了外部支付回滚。

即时自测

Actor 中的 async 方法在整个方法返回之前都不会被其他调用插入。
