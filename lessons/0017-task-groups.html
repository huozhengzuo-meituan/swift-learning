TaskGroup：动态并发、结果顺序与失败

处理长度未知的列表时，将并发收集与结果排列分开。

前置：16 async let：固定数量的结构化子任务

本课的一个成果实现一个按输入顺序返回结果的异步映射。

让子任务返回值

orderedMap 接受输入数组与 @Sendable 异步转换。每个子任务只处理一个值并返回 (原索引, 结果)，由父任务遍历任务组并修改结果数组。避免在多个子任务里捕获同一个 var results 后 append：那会把结果收集变成共享可变状态问题。任务组描述谁属于这次工作，父任务描述如何汇总，职责非常清楚。

group.addTask {
    try Task.checkCancellation()
    return (index, try await transform(input))
}
// 仅父任务收集，不让各子任务修改同一数组。
for try await result in group { indexed.append(result) }

完成顺序与业务顺序

任务组的迭代提供已经完成的结果，并不保证与 addTask 顺序相同。列表 UI 往往要求顺序稳定，因此示例最后按索引排序，再提取数值。[3,1,2] 的平方必须是 [9,1,4]，不能因为 1 最先完成就把它摆到开头。这个例子教学上一次创建全部任务；面对成千上万张图片，应使用有限并发窗口，完成一个再补一个，避免同时发起所有请求。

return indexed
    .sorted { $0.0 < $1.0 }
    .map(\.1) // 去掉仅用于还原顺序的索引。

通过消费结果传播失败

withThrowingTaskGroup 本身并不意味着任何子任务失败都会立刻被父任务观察到。示例通过 for try await 持续消费；一旦错误从闭包逃出，剩余子任务会被取消，作用域还会等待它们收尾。groupErrorCancelsAndJoinsSibling 测试先确保兄弟任务已经开始，再让另一任务失败，因此验证了真实生命周期。若产品允许部分成功，应显式让子任务返回 Result 并制定汇总策略，不要把错误吞成空数组。

验收现象

正常路径输出保持输入次序；故障路径会取消并等待兄弟任务。

先独立完成，再展开参考解法

正确实现携带索引，而不是按结果值排序。按结果排序会错误地得到 [4,9,16]，破坏输入项与结果的对应。示例 sorted 比较 $0.0 与 $1.0，正是对原始索引排序。

let values = try await orderedMap([4, 2, 3]) { value in
    try await Task.sleep(for: .milliseconds(value))
    return value * value
}
print(values) // [16, 4, 9]

从前端迁移时，留意这些误区

  • 把 Promise.all 的数组顺序直接套给任务组迭代。
  • 为每个大列表元素无上限创建网络请求。
