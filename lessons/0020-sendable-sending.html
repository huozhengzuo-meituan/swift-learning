Swift 6 与并发 / 30 MIN

Sendable、@Sendable 与 sending

Swift 6 的诊断是在询问数据由谁持有、谁还能改它，而非要求你到处加关键字。

前置：19 Actor：隔离状态与 await 后的不变量

本课的一个成果用不可变快照跨隔离传值，并区分可共享类型与一次安全转移。

Sendable 描述跨隔离使用的安全性

ReadingSnapshot 是字段均可安全传递的值类型，显式声明 Sendable 让边界易读。值类型并非自动安全：struct 若装着一个共享可变 class，仍须检查它的成员。actor 引用可以传递，因为它把内部可变状态留在隔离边界里。不要把 Sendable 翻译成“只读”：一个局部结构体仍可修改自己的副本；真正要避免的是跨任务同时访问同一份未受保护状态。

struct ReadingSnapshot: Sendable {
    let title: String
    let minutes: Int
}
let snapshot = ReadingSnapshot(title: "Swift", minutes: 25)

@Sendable 检查闭包捕获

@Sendable 标注函数值可安全跨并发边界使用。示例格式化闭包捕获 let suffix，它是可传递的 String；若捕获外部 var 并修改，编译器就有理由拒绝。@Sendable 不会自动把闭包派发到后台，也不等于 @MainActor。遇到诊断，先改成参数、值快照或 actor 操作；@unchecked Sendable 是你承担证明义务的承诺，不能充当绕过编译器的默认答案。

let suffix = "分钟"
let text = describe(snapshot) { item in
    "\(item.title) · \(item.minutes)\(suffix)"
}
print(text)

sending 是交接，不是通行证

Swift 6.0 的 sending 可以表达：这个非 Sendable 值在边界处与原隔离区断开，可安全交给新持有者。Draft 是可变 class，DraftInbox.accept 接收 sending Draft 后保存它；调用方不再访问已交接的引用。若原位置还保留可访问别名，编译器会分析潜在冲突。这个概念接近转移所有权，但不必把 Swift 所有引用都想成 Rust 的唯一所有权。6.2 的调用者隔离是另一项演进，不要与 sending 混为一谈。

let inbox = DraftInbox()
let draft = Draft(title: "交接完成")
await inbox.accept(draft)
// 后面只通过 inbox 读取；不再触碰 draft。
print(await inbox.title() ?? "")

验收现象

快照可以安全传值；Draft 被交接后原隔离区不再使用它。

先独立完成，再展开参考解法

若 UI 只需显示标题，传 ReadingSnapshot 最清楚；若一个新建草稿要整体交给 actor 持有，sending 可以避免伪造 Sendable 一致性。原引用继续写 title 会和 actor 读取同一对象冲突，因此不是“编译器太严格”，而是所有权设计还不完整。

从前端迁移时，留意这些误区

  • 看到并发错误就添加 @unchecked Sendable。
  • 认为 let class 引用意味着对象所有属性不可变。

即时自测

跨 actor 传递的值，应满足该传递方式要求的并发安全约束。
