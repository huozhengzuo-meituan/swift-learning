身份与列表：状态为什么会保留或重置

React key 的经验很有帮助，但还需要把身份与 SwiftUI 的局部存储、导航和异步任务生命周期联系起来。

前置：28 Observation：共享模型、所有权与隔离

本课的一个成果用稳定 ID 列表，并在筛选状态下删除正确条目。

身份回答是不是同一个元素

ForEach 需要可标识数据或明确 id。StudyItem 初始化时生成 UUID，修改标题、切换完成状态、重新排序时仍使用同一 ID。不要写计算属性 var id: UUID { UUID() }，那意味着每次读取都换一个身份；也不要用可编辑标题当身份，否则改名会被当成删除旧视图再插入新视图。身份影响 State 的关联、选择状态与动画，并非只用于消除编译错误。

@Model
final class StudyItem {
    @Attribute(.unique) var id: UUID
    var title: String
    // id 在初始化时生成一次，之后随数据持久保存。
}

删除的索引属于当前展示集合

示例 visibleItems 先执行搜索和完成状态筛选，然后 ForEach 展示结果。.onDelete 给出的 IndexSet 是这个结果集合的偏移量。如果拿它去索引原始 items，在隐藏条目存在时就会删错数据。先将当前偏移映射为模型或稳定 ID，再提交删除。列表过滤适合课程的小规模数据；大规模列表应考虑 Query predicate，不能把所有数据库记录拉到内存后无限过滤。

ForEach(visibleItems) { item in
    NavigationLink(value: item.id) { StudyRow(item: item) }
}
.onDelete { offsets in
    let targets = offsets.map { visibleItems[$0] }
    delete(targets)
}

有意重置与无意丢失不同

详情使用 .id(item.id)，意味着切换到另一学习条目时重建详情的局部加载器和重试计数。这是明确的产品选择；如果要跨条目保留编辑进度，草稿必须搬到更长寿命的拥有者。不能在根视图随便加 .id(UUID()) 强行刷新，那会反复销毁状态、取消任务、丢失焦点。结构性 if 分支也影响身份，因此调整结构时要观察输入框和任务是否重建。

StudyDetailView(item: item) {
    editor = EditorRequest(item: item)
}
.id(item.id) // 仅在选择另一条数据时重建详情局部状态。

验收现象

仅 SwiftUI 被删除，其余两条保留；标题修改不会生成新的模型 ID。

先独立完成，再展开参考解法

保留 visibleItems 的偏移映射。可在断点观察目标 ID，或为 StudyWriter.delete 增加使用特定模型数组的测试；不要用原始 items[offset]。

let targets = offsets.map { visibleItems[$0] }
try StudyWriter.delete(targets, in: context)

从前端迁移时，留意这些误区

  • 不要用随机 ID 强制刷新整棵视图。
  • 不要把筛选结果的索引当成原始数据的索引。
