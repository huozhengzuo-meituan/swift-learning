Task 生命周期与合作式取消

页面消失、搜索词改变、用户点击停止都需要明确的任务所有者。

前置：17 TaskGroup：动态并发、结果顺序与失败

本课的一个成果持有 Task 句柄、发出取消信号，并验证工作主动退出。

Task 是有所有者的工作

Task { ... } 创建非结构化任务，适合把同步事件连接到异步入口，但它不是自动属于当前函数的结构化子任务。创建处可以继承 actor 上下文等信息，却不会因此自动获得父子生命周期与取消传播。保存句柄，明确谁调用 cancel、谁观察 value、何时释放持有者。丢弃句柄不会等于取消；同样，Task.detached 也不是常规 UI 加速按钮。

let task = Task { try await cancellableSum(upTo: 100_000) }
task.cancel() // 发出请求，不会强行终止工作。
do { print(try await task.value) }
catch is CancellationError { print("已退出") }

让取消在合理位置生效

cancellableSum 的循环没有自然 I/O 等待，因此每次迭代检查取消，并间隔调用 Task.yield 让其他任务有调度机会。yield 不保证某个特定任务立即运行，也不是业务同步原语。Task.sleep 自己支持取消；一般的 await 并不自动检查取消。检查频率是性能与响应性的取舍，大数据转换可每批检查一次。这里数字上限很小，重点是控制流而非求和算法。

for value in 0..<limit {
    try Task.checkCancellation()
    sum += value
    if value.isMultiple(of: 100) { await Task.yield() }
}

取消不能代替资源收尾

一旦创建了流、订阅或外部请求，就需要把终止信号传给对应资源。defer 适合同步清理；withTaskCancellationHandler 的 onCancel 是同步闭包，可能与 operation 并发执行，所以不能随便共享普通可变变量。也不要把所有异常都显示为红色错误：用户主动离开页面的取消通常回到 idle。测试使用门闩先固定任务状态再取消，比“先 sleep 一会儿再 cancel”可靠。

验收现象

演示观察到 CancellationError；测试保证真正计算开始前取消信号已发出。

先独立完成，再展开参考解法

测试先让任务进入 Gate 等待，再取消它，最后打开门闩。进入求和函数时取消标记已经设置，第一次 checkCancellation 就会抛错。Gate 只负责测试同步，不是业务线程锁，也不证明所有非结构化任务会自动取消。

await gate.waitUntilEntered()
task.cancel()
await gate.open()
// await task.value 应抛出 CancellationError。

从前端迁移时，留意这些误区

  • 把取消理解为杀线程。
  • 认为每个 await 都会自动抛 CancellationError。

即时自测

取消是协作机制，长循环需要主动检查任务的取消状态。
