State 与 Binding：找到唯一数据源

核心问题不是“该套哪个包装器”，而是“谁持有值、谁需要读、谁被授权写”。

前置：26 布局与修饰器：理解包裹顺序

本课的一个成果把编辑表单拆成父级草稿与子级笔记编辑器，并保留取消语义。

State 给视图身份提供状态存储

普通 struct 的属性描述输入；@State 表示由 SwiftUI 管理的局部存储。StudyEditorView 持有 StudyDraft，界面读取 draft 后依赖它的变化。State 的初始值不是每次父视图传入参数变化时都重新覆盖，所以编辑另一条记录必须给编辑器合适的身份。示例 sheet 使用独立 EditorRequest，避免把上一次表单残留当成新记录。不要为了同步 props 盲目复制出多份 State。

@State private var draft = StudyDraft()

var body: some View {
    TextField("Title", text: $draft.title)
    // draft.title 是当前值，$draft.title 是读写通道。
}

Binding 借用读写通道，不拥有第二份值

子视图只展示时传 let 值；需要编辑时传 Binding。NotesField 的 @Binding text 指向父级 draft.notes，TextEditor 写入的正是父级数据。它不是每次复制一个 String 并让两份值自动同步。自定义 Binding(get:set:) 能把 alert 的显示状态映射到可选错误字符串，但 setter 必须维护一致性，例如关闭 alert 后清除 errorMessage，而不是把错误永久留着。

struct NotesField: View {
    @Binding var text: String
    var body: some View {
        TextEditor(text: $text)
            .accessibilityLabel("Notes")
    }
}
// 父级：NotesField(text: $draft.notes)

草稿使取消操作有准确含义

SwiftData 的 StudyItem 是被 context 追踪的对象。若直接将编辑框绑定到 item.title，用户每次输入都已经改变共享模型，点击取消不能仅仅 dismiss。示例先将字段复制到值类型 StudyDraft，保存时验证并应用到模型；取消只丢弃草稿。这与 Web 表单的受控输入相似，但这里还涉及本地持久化对象，必须明确提交边界。新课程 UI 状态默认留在 MainActor 内。

init(item: StudyItem?, onSave: @escaping (UUID) -> Void) {
    self.item = item
    self.onSave = onSave
    _draft = State(initialValue: StudyDraft(
        title: item?.title ?? "",
        notes: item?.notes ?? ""
    ))
}

动手：验证编辑后取消不会改变原条目，并给子编辑器增加实时字符数。

  1. 新建一条标题为 Original 的记录，打开编辑修改内容后取消。
  2. 重新打开，确认原标题没有被改变。
  3. 在 NotesField 内添加 Text(text.count.formatted())，输入时观察数字。
验收现象

取消后仍为 Original；字符数与输入即时同步，父子没有重复状态。

先独立完成，再展开参考解法

字符数是 text 的派生值，不需要 @State var count，也不需要 onChange 手动同步。

VStack(alignment: .leading) {
    TextEditor(text: $text)
    Text(text.count.formatted()).font(.caption)
}

从前端迁移时，留意这些误区

  • 不要把初始值当成持续同步机制。
  • 不要把可以计算得到的字符数重复保存为状态。
