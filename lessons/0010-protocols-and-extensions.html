用协议表达能力，用扩展共享实现

先从真实调用者需要的两个属性与一个方法提炼协议。不要为了“架构感”给每个类型都建立对应协议。

前置：09 用枚举排除不可能的状态

本课的一个成果让不同学习项目提供相同摘要接口，并理解协议要求与默认实现。

协议声明调用者可以依赖的能力

protocol 描述要求，不直接存放实例数据。{ get } 表示调用者只要求能读取，符合类型可以用 let、var 或计算属性满足它。struct、enum、class 都能符合协议，不需要共同父类。与 TypeScript 的结构化匹配不同，Swift 通常要求显式声明 conformance；只是碰巧有同名成员不会自动变成协议实现。

public protocol StudyDescribing {
    var studyTitle: String { get }
    var studyMinutes: Int { get }
    func summary() -> String
}
extension StudySession: StudyDescribing {
    public var studyTitle: String { title }
    public var studyMinutes: Int { minutes }
}

默认实现减少重复，要求本身仍要明确

协议扩展可以提供默认实现。将 summary 写在协议要求中，再在 extension 中提供默认版本，符合类型可以自行实现替代版本。若方法只存在于 extension 而不在协议要求中，通过协议或泛型视角调用时可能不会采用你期待的同名实现。初学时把需要动态替代的能力写成协议要求，避免把扩展当成 JavaScript prototype 覆盖机制。

public extension StudyDescribing {
    func summary() -> String {
        "\(studyTitle)：\(studyMinutes) 分钟"
    }
}
let session = StudySession(title: "协议", minutes: 25)
print(session.summary())

组合能力，不扩大对象的职责

Reading 可以符合相同协议，却没有 complete 方法或 isCompleted 属性；摘要调用者不该因此强迫阅读材料伪装成完整学习任务。协议边界应由消费方的需求驱动。extension 适合补充方法、计算属性和协议符合；不能给已有类型直接添加实例存储属性，存储职责仍在原类型中。

标准库 Equatable、Hashable、Codable 也遵循能力组合思路。Hashable 不只是“有一个叫 hash 的字段”，它与相等语义有关；自定义类型通常先借助编译器合成，等遇到真实需求再自定义。下一课会讨论“一个符合协议的具体类型”和“装着任意实现的容器”之间的差异。

验收现象

默认 Reading("阅读", 10) 返回 阅读：10 分钟；自定义 summary 后，通过 any StudyDescribing 调用也采用该要求的实现。

先独立完成，再展开参考解法
public struct Reading: StudyDescribing {
    public let studyTitle: String
    public let studyMinutes: Int
    public init(title: String, minutes: Int) {
        studyTitle = title
        studyMinutes = minutes
    }
    // 可选：不写此方法时使用协议扩展的默认实现。
    public func summary() -> String { "阅读：\(studyTitle)" }
}

如果保留此定制，descriptions 测试中第一项预期改成“阅读：阅读”。这不是为了迎合实现随便改断言，而是你明确改变了展示契约。

从前端迁移时，留意这些误区

  • 协议不是 TypeScript interface 的完全等价物，符合关系需要显式声明。
  • extension 不能随意为类型补上实例存储属性。
