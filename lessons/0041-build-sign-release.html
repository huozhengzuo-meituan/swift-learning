从本地构建走到可交付版本

Web 的部署通常更换服务器上的文件；原生发布还涉及设备可执行代码、签名身份、系统权限和用户本地数据。

前置：40 把文件、偏好和敏感数据放在正确位置

本课的一个成果区分 build、test、archive、签名与分发，并完成发布前证据清单。

一个成功构建只回答一个问题

build 检查某个 SDK、配置与目标是否能产生二进制；test 执行选定测试；archive 为分发组织产物。模拟器的成功构建不能证明 iPhone 真机运行，更不能证明可上传商店。CODE_SIGNING_ALLOWED=NO 用于本课程本地构建检查，不能据此获得可分发到用户设备的应用。

Bundle Identifier 是应用身份的一部分；Marketing Version 是用户可见版本；Build Number 标识构建。保持开发、测试和发布配置可追踪，记录工具链、源代码版本、依赖和构建参数。

选择发布路径后再配置身份

iOS 通常通过 App Store Connect / TestFlight 做测试分发和上架；实际所需账号、证书和描述文件按 Apple 当前规则核对。Mac 除 Mac App Store 外，也可通过 Developer ID 签名和公证后直接分发。公证不等于 App Review，也不验证你的业务功能。

课程不会替你创建账号、购买会员、签名或上传应用。学习任务是理解流程并准备可审阅产物。实际分发时先完成图标、权限用途、隐私信息、版本元数据和真机验证，再按目标渠道执行。

CI 让证据可重现

运行 scripts/verify.sh，把包测试和两个平台的无签名构建串起来。CI 应固定 Xcode 版本与目标系统，保留失败日志或 xcresult；不要仅存一行“成功”。Release 验收要覆盖从旧数据升级、低存储、网络失败、后台恢复和可访问性。

# 根目录；不上传、不签名、不发布
bash scripts/verify.sh

# 显式查看本机可用工具与目标
xcodebuild -version
xcrun simctl list devices available

发布前检查当前 App Store 上传要求。文档会变化，本课给出流程框架与官方入口，不把某一年的最低 Xcode 版本写成永久规则。

完整工程验证脚本

bash scripts/verify.sh

终端命令默认在 swift-learning 根目录执行；说明为 Xcode 操作时，跟随项目 README。

动手：准备一份不会混淆验证范围的交付记录

  1. 运行根目录 scripts/verify.sh。
  2. 写出本机 Xcode、Swift、SDK、最低部署版本和实际测试 OS。
  3. 根据 CAPSTONE.md 标出未完成的真机、旧版系统与分发项。
  4. 在 Xcode 看 Archive 工作流，理解所需身份；本练习不提交上传。
验收现象

能向同事明确说明“什么已验证、在哪验证、还有什么未验证”，而非只说编译通过。

先独立完成，再展开参考解法

记录例如“macOS scheme build 成功；iOS simulator build 成功；Swift Testing 通过；设备交互与签名分发未做”。把最低部署版本与实际测试 OS 分开，列出发布目标所需的下一步。CI 使用同样命令并保留结果，不把测试覆盖描述成全平台保证。

从前端迁移时，留意这些误区

  • 不要把证书、令牌、密码提交到仓库。
  • 项目最低支持 iOS17，不代表你已经在 iOS17 设备上测过。

即时自测

模拟器构建、设备 archive 与签名分发需要分别完成并验证。
